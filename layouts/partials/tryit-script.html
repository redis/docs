Emitted by every shortcode that renders such a button — layouts/shortcodes/redis-cli.html and layouts/partials/tabs/wrapper.html — and idempotent: each definition is guarded with `||`, so a page that renders it a dozen times still has one implementation. It used to be two inline copies that had drifted, and which copy won on a given page came down to which shortcode Hugo rendered first. Page setup. Every block marked `prereq="true"` adds a part to this page's setup (window._tryItSetup.parts, in document order) and carries data-tryit-setup on its own button. Any other "Try it" here runs the parts first, so a reader who lands half way through a tutorial and clicks an FT.SEARCH gets the index it searches rather than SEARCH_INDEX_NOT_FOUND. Parts rather than one block, because a page's setup is not always one block: on the data-modeling step, product:1 is written by the example that introduces JSON.SET and product:2 onwards by the block that loads the rest, so a reader who ran only the second one and then asked for product:1 got nil. A part clicked directly runs only itself: it *is* setup, so it needs none. Any other "Try it" gets every part the sandbox has not had yet. The workbench is told about the parts separately from the snippet (see js/redis-workbench.js) so it can skip the ones the sandbox has already had this session; the standalone CLI gets a fresh session every time, so there they are simply prepended. `data-needs-prereq` / window._tryItPrereqs is the older per-set model, kept for pages that mark a prereq example without a page-level setup.
