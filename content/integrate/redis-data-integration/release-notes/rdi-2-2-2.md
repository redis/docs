## What's New in 2.2.2

### Compatibility Notes

- **New operating system requirements in RDI 2.4.0**: For virtual machine (VM) installations, RDI 2.4.0 and later require RHEL 9 or Ubuntu 22.04, 24.04, or 26.04. RHEL 8 and Ubuntu 20.04 boot with cgroup v1 by default, while RDI 2.4.0 installs a K3s version that requires cgroup v2. If your RDI VMs run RHEL 8 or Ubuntu 20.04, move to a supported operating system before you upgrade to RDI 2.4.0, in one of these ways:

  - Upgrade the operating system of your VMs in place.
  - [Move RDI to new VMs](/content/integrate/redis-data-integration/installation/install-vm.md#move-rdi-to-new-vms).

### Breaking Changes

- **Upgrading a Helm installation with leader election from a version before 1.18.1**: If `operator.leaderElection.enabled` is `true`, run `kubectl delete deployment rdi-operator -n <namespace> --cascade=foreground` right before `helm upgrade`, which recreates the operator. Start the upgrade as soon as the command returns, so that the new operator starts within the lease time to live (TTL) of the installed version, 60 seconds by default. See [Delete the operator Deployment](/content/integrate/redis-data-integration/installation/upgrade.md#delete-the-operator-deployment).

### Bug Fixes

- **Configurations of installations upgraded from a version before 2.0.0 failed table validation**: After such an upgrade, using `redis-di deploy` with the unchanged configuration could fail table validation with access denied for the user `${SOURCE_DB_USERNAME}`. Also, `redis-di list-secrets` did not list the source, and changing the source or target secrets restarted no component. The upgrade of a VM installation now fixes this. For a Kubernetes installation, [label the source and target secrets](/content/integrate/redis-data-integration/installation/upgrade.md#label-the-source-and-target-secrets).
- **Upgrading from a version before 2.0.0 switched pipelines to the Flink processor**: After the upgrade, a pipeline without `processors.type` ran the Flink processor. The upgrade now sets `processors.type` to `classic` on such a pipeline. Also add `processors.type: classic` to your `config.yaml`, so that the pipeline keeps the classic processor when you next run `redis-di deploy`. If you replace an RDI 1.19.1 instance, such as a VM, with a new one of this version, first deploy `processors.type: classic`. See the [upgrade steps](/content/integrate/redis-data-integration/installation/upgrade.md#upgrade-steps) for your version.
- **Certificates set in a version before 2.0.0 could not be deleted**: After an upgrade from a version before 2.0.0, `redis-di delete-secret` previously failed with a not found error for a source or target certificate set from a file with a name other than `ca.crt`, `client.crt`, or `client.key`. Also, `redis-di list-secrets` listed it as a simple secret, next to an extra secret for a file without an extension. The VM upgrade now stores these certificates under their default file names. If the upgrade warns that a certificate was not moved, set it again with `redis-di set-secret`.
- **Configurations from an earlier release failed validation with properties that RDI manages**: `redis-di deploy` previously failed with a configuration that sets any of the following properties, even though an earlier release accepted them:

  ```yaml
  sources:
    <source-name>:
      advanced:
        source:
          topic.delimiter: <value>
          offset.storage.redis.key: <value>
          schema.history.internal.redis.key: <value>
          database.ssl.keystore: <value>
          database.ssl.keystore.password: <value>
          mongodb.ssl.keystore: <value>
          mongodb.ssl.keystore.password: <value>
        riotx:
          streamPrefix: <value>
  processors:
    advanced:
      source:
        stream.name.pattern: <value>
        consumer.group: <value>
      processor:
        counters.key: <value>
  ```

  This failure no longer happens. RDI ignores these properties and uses its own values, so remove them from your configuration.
- **Upgrading a VM installation from a version before 1.18.1 could leave components of the old version running**: The operator of the old version could recreate a component, such as the classic processor, next to the components of the new version. The upgrade now stops the old operator before it starts the new one.
